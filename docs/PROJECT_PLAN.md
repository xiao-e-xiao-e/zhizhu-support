# 知助 · 智能客服与知识协作平台项目计划书

编制日期：2026-10-26。项目起点：现有 Vue 3、FastAPI、BGE 和 ChromaDB 知识库问答系统。首版面向一个软件产品团队，完成从资料维护、智能排查、人工工单到知识更新的业务闭环。

## 1 项目目标

帮助软件产品用户获得有依据的操作指导和问题排查建议；资料不足时主动补全信息或转交客服；将经过审核的解决方案沉淀为可复用知识。

首版交付一个可以部署、能够管理用户权限、数据可持久化、智能效果可评估的 Web 应用。现有代码作为基础增量演进。外部正式发布以通过本计划的上线验收为前提。

## 2 用户与权限

| 角色 | 主要操作 | 数据范围 |
|---|---|---|
| 管理员 admin | 创建账号、分配角色、维护知识、处理工单 | 团队发布的知识；本人会话；团队工单 |
| 客服 staff | 维护知识、回复和流转工单、编写 FAQ 草稿 | 团队发布的知识；本人会话；团队工单 |
| 用户 user | 提问、反馈、创建和跟进工单 | 团队发布的知识；本人会话与工单 |

首版采用单团队部署，不提供公共注册。账号由管理员创建。用户身份由服务端会话确定，客户端提交的用户 ID、角色或提示词不能决定授权。管理员也不默认读取其他用户的私人会话。

多企业 SaaS、付费订阅、跨团队共享、语音客服、移动端和多 Agent 编排列入后续版本。

## 3 业务流程

1. 管理员上传产品手册、FAQ、版本说明，完成解析、校验并发布。
2. 用户描述问题；助手结合历史上下文识别缺少的版本、环境和报错信息。
3. 助手检索适用资料，返回有引用的排查建议；无依据时明确说明。
4. 用户反馈是否解决；未解决时生成工单草稿。
5. 用户核对后提交工单，客服接单、回复、解决，用户确认关闭。
6. 客服从解决记录提炼 FAQ，知识管理员审核发布。

工单状态：新建 → 处理中 → 已解决 → 已关闭。已解决的问题可以重新打开。每次状态变化记录操作者、时间和说明。

## 5 技术方案

前端继续使用 Vue 3、TypeScript、Pinia 和 Element Plus。后端继续使用 FastAPI，业务逻辑分为路由、服务和数据访问层。

- PostgreSQL 保存用户、登录会话、对话、工单、反馈、文档元数据及任务记录。SQLAlchemy 管理数据访问，Alembic 管理版本迁移。开发和快速测试支持 SQLite；正式部署使用 PostgreSQL。
- ChromaDB 继续保存向量。知识检索先限定发布范围，再执行召回；多租户能力上线前必须在数据层增加租户过滤。
- 登录使用随机不透明凭证，数据库只保存凭证散列；浏览器使用 HttpOnly、SameSite Cookie。生产启用 Secure，写请求校验来源，登录尝试具有限流。
- 模型 API Key、Base URL 和模型名由服务端配置。公开接口不接受任意模型地址，避免服务端密钥被发送到外部地址。
- 会话和消息携带用户归属，所有读写和导出都验证所有者。旧 chat_history.json 不自动分配给新用户，由管理员显式指定导入归属并保留原文件。
- 文档入库逐步迁移到独立 worker 和持久化任务队列。原始文件采用持久化卷，后续按需要接入对象存储。
- 首版部署采用 Docker Compose：前端静态服务、API、PostgreSQL、Chroma 服务和 worker。M3 使用 PostgreSQL 持久化租约队列完成领取、续租和重试，暂不增加 Redis；后续任务量增长时再评估迁移。

## 6 智能能力设计

### 6.1 多轮与检索

优先使用服务端保存的最近会话历史，控制消息数量与总字符预算。首阶段先支持模型理解历史；查询改写、关键词加向量混合检索和 reranker 在固定评估集上比较后接入。相似度仅表示检索相关性，不标注为答案正确率。

### 6.2 Agent 工具

工具包括 search_knowledge、search_resolved_tickets、get_ticket_status、create_ticket。模型生成工具参数，后端验证身份、权限和字段。创建工单先展示待提交内容，由用户确认。每次运行限制步骤数、时长、调用成本；写操作使用幂等键并记录执行结果。

检索片段按资料处理，不能改变系统规则或授予工具权限。界面展示引用、工具名称、执行状态和结果，不输出模型隐藏推理。

### 6.3 评估

建立 50 至 100 条经过人工标注的问题，覆盖常规问答、多轮指代、错误码、版本冲突、无答案、越权和提示注入。记录期望文档、关键答案及预期工具动作。开发集与验收集分开，避免只针对固定例子调优。

指标包括 Recall@5、引用正确性、无依据回答比例、工具成功率、首字时延、整体时延、失败率和单次成本。自动评分配合人工抽查。质量门槛在基线评估后确定，不以未经测量的准确率作为项目成果。

## 8 里程碑与实施顺序

以下人日仅作单人全职开发的工作量估算，不构成交付日期承诺。实际安排依据每个版本的验收结果调整。

| 里程碑 | 估算 | 交付物 | 退出条件 |
|---|---|---|---|
| M1 工程与身份基础 | 4 至 6 人日 | 环境、登录、RBAC、数据库会话、迁移、前端登录和账号管理、基础测试与部署模板 | 未登录拒绝业务访问；跨用户会话隔离；重启可读；构建和测试通过 |
| M2 客服业务闭环 | 5 至 7 人日 | 产品知识、工单、反馈、状态与审计 | 用户提问后可建单，客服处理，用户确认；权限测试通过 |
| M3 知识与问答质量 | 5 至 7 人日 | 异步入库、文档版本、查询改写、检索对比、评估基线 | 入库失败可重试；版本可追溯；输出可复现的评估报告 |
| M4 智能工作流 | 4 至 6 人日 | 工具调用、人工确认、FAQ 草稿审核、运行追踪 | 写操作确认与幂等生效；工具超时和失败可恢复 |
| M5 上线验收与试运营 | 3 至 5 人日 | HTTPS、限流、压测、备份恢复、发布与回滚手册、试用记录 | 通过下述验收清单，邀请真实用户试用并处理阻断问题 |

预计总工作量为 21 至 31 人日。外部模型、服务器和域名费用以实际选型另行核算。当前 M1 至 M4 的核心能力已实现，M4 的使用和验收记录见 M4_ACCEPTANCE.md；下一阶段为 M5 上线验收与试运营。详细交付与验证结果维护在 EXECUTION_LOG.md，知识和业务流程见 M3_ACCEPTANCE.md、M2_ACCEPTANCE.md。

## 9 验收与发布条件

- 用户能登录、提问、跟进自己的工单；客服能处理工单；管理员能维护知识和账号。
- 未登录、越权、过期会话、非法状态变化和不合法文件都有明确错误响应。
- 会话、工单、资料元数据在服务重启后保持；执行一次备份恢复演练并核对数据。
- SSE 通过反向代理持续输出；超时、取消和模型异常不会导致静默丢失或重复写入。
- 固定评估集、接口测试和前端构建通过；提示注入和权限隔离用例无阻断问题。
- 在约定的测试硬件、数据规模和并发下提交时延与失败率报告；容量目标在首轮压测后确定。
- 配置生产密钥、HTTPS、允许的来源、文件与调用配额；验证日志不包含密码、登录凭证和 API Key。
- 部署、数据库迁移、备份、恢复和回滚步骤可重复执行，监控能识别数据库和模型不可用。

## 10 风险与应对

| 风险 | 应对 |
|---|---|
| 模型生成错误排查步骤 | 文档引用、无答案处理、用户反馈、人工工单兜底、评估回归 |
| 资料过时或版本混用 | 版本与发布状态过滤、来源展示、知识审核 |
| 会话或工单数据越权 | 服务端归属校验、RBAC、接口级负向测试 |
| 上传阻塞和索引不一致 | 后台任务、幂等、状态持久化、索引版本与补偿 |
| 工具重复执行或权限过大 | 最小权限、确认、幂等键、执行预算和审计 |
| 本地环境与部署环境差异 | 锁定依赖、SQLite 和 PostgreSQL 分别测试、容器化与 CI |
