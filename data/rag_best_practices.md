# RAG 系统最佳实践

## 什么是 RAG

RAG（Retrieval-Augmented Generation）结合了信息检索和文本生成两个阶段：
1. **检索阶段**：从知识库中找到与用户问题最相关的文档片段
2. **生成阶段**：将检索到的上下文与用户问题一起提交给大模型，生成有依据的回答

## 文档处理

### 分块策略

分块（Chunking）是 RAG 系统中最关键的预处理步骤之一。

**推荐做法：**
- 保持语义完整性：尽量在段落边界切分，不要生硬截断
- 适度重叠：相邻 chunk 之间保留 10-20% 的重叠，避免关键信息被切断
- 考虑文档类型：代码文档可以按函数切分，长文可以按章节切分
- 经验值：chunk 大小在 300-800 字符之间效果最好，具体取决于嵌入模型

**常见错误：**
- Chunk 太大：检索精度降低，噪声增多
- Chunk 太小：丢失上下文，碎片化严重
- 不分块直接检索：大文档中难以定位精准答案

### 元数据保留

为每个 chunk 保留元数据非常重要：
- 来源文件名和路径
- 在原文中的位置（页码、行号等）
- 文档类型和创建时间
- 自定义标签和分类

这些元数据可以用于：
- 结果过滤（只看某类文档）
- 来源追溯（回答中引用出处）
- 排序加权（新文档优先级更高）

## 嵌入模型选择

### 关键指标

| 指标 | 说明 | 重要性 |
|------|------|--------|
| 检索精度 | MTEB/MTEB-CN 基准分 | 最关键 |
| 向量维度 | 通常 768-3072 维 | 影响存储和速度 |
| 最大输入长度 | 单次可编码的 token 数 | 影响 chunk 大小上限 |
| 多语言支持 | 是否支持中英文混合 | 双语场景必需 |

### 推荐模型（2026）

- **text-embedding-3-large** (OpenAI): 3072 维，综合最佳
- **text-embedding-3-small** (OpenAI): 1536 维，性价比高
- **bge-large-zh** (BAAI): 中文场景表现优秀
- **jina-embeddings-v3** (Jina AI): 支持 8192 token 长文本

## 检索优化

### 混合检索

单一检索方式各有盲区：
- **语义检索**（向量相似度）：擅长理解含义，但可能漏掉精确关键词
- **关键词检索**（BM25）：擅长精确匹配，但不理解语义

**推荐：混合使用两种检索并融合排序。** ChromaDB 等向量数据库已原生支持。

### Rerank（重排序）

在初检索后增加 Rerank 步骤，用更强但更慢的模型重新排序：
- 初检索用轻量模型召回 Top-50
- Rerank 模型精排后保留 Top-5
- 显著提升答案质量，成本增加不大

### 相似度阈值

设置合理的相似度阈值可以过滤无关结果：
- 阈值过高 → 可能漏掉相关但表述不同的内容
- 阈值过低 → 噪声干扰大模型判断
- 起点建议 0.5，根据实际效果调整

## 提示词设计

### RAG 专用 System Prompt 要点

1. **明确角色**：告知模型它是知识库助手
2. **约束行为**：只根据提供资料回答，不得编造
3. **处理不确定性**：资料不足时明确表态
4. **引用规范**：要求注明参考来源
5. **格式要求**：规定输出格式（列表、表格、段落等）

### 上下文组装

检索到的文档片段需要合理组装：

```
[资料 1 | 来源: xxx.md]
相关内容...

[资料 2 | 来源: yyy.pdf]
相关内容...

用户问题：{question}
```

关键原则：
- 按相似度从高到低排列
- 每条资料标注来源
- 总长度控制在模型上下文窗口的 50% 以内，留足回答空间

## 评估与迭代

### 评估指标

| 指标 | 含义 | 测量方式 |
|------|------|----------|
| 检索命中率 | 相关文档是否被召回 | 人工标注+自动计算 |
| 答案准确性 | 回答是否基于文档 | LLM-as-Judge |
| 答案完整性 | 是否覆盖了所有关键信息 | 人工评估 |
| 引用正确率 | 来源引用是否准确 | 人工检查 |

### 迭代流程

1. 建立评估集（至少 30 个问答对）
2. 调整参数（chunk 大小、top_k、温度、相似度阈值）
3. 运行评估并记录各项指标
4. 找到最佳参数组合
5. 定期更新评估集，持续优化
